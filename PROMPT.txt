写论文和做课件的人需要一个在浏览器里就能用的 LaTeX 数学公式编辑器：一边敲 LaTeX 源码，一边实时看到排版渲染，还能管理一份文稿里的多个公式、在公式之间做交叉引用。我们要把它做成一个前后端配合的完整应用，界面在浏览器里交互，而真正决定正确性的解析、编号、校验工作放在后端完成，前端只负责编辑与呈现。这是一个数学公式创作工具，不是通用富文本文档协作，也不是代码托管，更不涉及账户体系与权限。

编辑界面：左侧是带行号的源码编辑区，对 LaTeX 有基本的语法高亮（命令、花括号、数学符号、注释用不同颜色区分），支持括号匹配高亮与花括号自动补全；右侧是实时渲染的预览区，中间可拖动调整两栏比例。用户停止输入约 150 毫秒后触发一次渲染，避免每敲一个字符就重排。界面下方有一个可折叠的符号面板，按希腊字母、运算符、关系符号、箭头、矩阵模板、常用结构分类罗列常见符号，点击即在光标处插入对应的 LaTeX 代码，并单独保留一栏最近使用过的符号。界面还提供一个公式模板库（定积分、矩阵乘法、正态分布、方程组等常用结构），点击插入完整骨架后再改参数。

多公式与交叉引用是这个工具的核心，也是后端必须严肃处理的部分。一份工作区里可以有多个公式，每个公式有一个自动分配的顺序编号和一个可选的标签。用户可以在公式 A 的源码里用 \ref{标签} 引用公式 B，渲染时该处显示为公式 B 的实际编号数字。用户还能拖拽调整公式顺序，一旦顺序变化，所有公式的编号要自动重排，并且所有交叉引用显示的数字要跟着更新到正确的新编号——这套「标签到编号」的解析与重排必须在后端完成并可被独立验证，不能只在前端糊一个映射。当引用指向一个不存在的标签，或者若干公式用了重复的标签、或者交叉引用之间形成了环（A 引用 B、B 又引用 A 的编号这类相互依赖若按你的编号规则会成环），后端要能检测出来并明确报出问题所在，而不是渲染出一个错误的数字。

LaTeX 的解析与错误定位也由后端负责，是另一处可验证内核。后端要对提交的公式源码做词法与括号结构的解析：花括号、\left \right、begin/end 环境是否配对，命令是否闭合。出现语法错误时，要尽量把错误定位到具体位置（第几行、第几个字符附近），并对常见错误给出可读的提示，比如缺少右花括号、或者把一个未知命令识别为某个已知命令的拼写错误并建议正确写法。还要支持一种容错渲染模式：即便源码里有局部语法错误，也尽量把能渲染的部分渲染出来，出错的片段用醒目的占位标记，而不是整个公式白屏。这些解析判断（配对检测、错误位置、拼写建议、容错切分）要有明确的输入输出契约，能被自动化测试逐条覆盖。

正确性判据要落到测试里守死：一份公式重新排序后，每个公式的新编号与所有 \ref 显示的数字必须与新顺序一致；引用不存在的标签、重复标签、成环引用都必须被检测并报错，而不是静默给出错号；一段缺失右花括号的源码，后端报出的错误位置要落在真正缺括号的地方附近；容错模式下，一处局部错误不能吃掉整段本可正确渲染的内容。工作区（含其所有公式、标签、顺序、自定义模板）要能持久保存到数据库，用户下次打开时原样恢复；多个工作区并发编辑保存时互不串写、互不覆盖。

前端用 React 配合 Vite 构建，后端用 Python 3.12 搭配 FastAPI，持久化用 PostgreSQL 16。请把系统按职责合理拆分为多个模块与文件：前端的编辑器组件、符号与模板面板、预览渲染各自独立；后端的 LaTeX 词法与结构解析、交叉引用编号解析与重排、错误定位与拼写建议、工作区持久化也各成一块，别让前端挤成一个巨型组件、也别让后端解析逻辑挤在单个文件里。整套系统经由 Docker Compose 编排：前端、后端服务与数据库一同拉起，浏览器打开页面后所有解析与渲染都走后端接口完成；随交付附上一组自动化测试，覆盖编号重排、交叉引用的三类异常检测、错误位置定位与容错渲染。运行环境固定为：前端构建用 Node.js 20，后端用 Python 3.12，数据库用 PostgreSQL 16。
